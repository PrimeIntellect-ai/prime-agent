# Telemetry contract and rollout

Telemetry is enabled by default. It records observed use, delays, and failures so Prime Agent can be improved. It does not establish how many people installed the product, whether a task was solved, or what happened on opted-out installations.

## Consent and content

`telemetry.enabled=false`, `PRIME_AGENT_TELEMETRY=0`, `DO_NOT_TRACK=1`, and offline mode disable reporting. Offline mode and Do Not Track take precedence over the environment enable override. `PRIME_AGENT_TELEMETRY=1` retains its existing explicit override of settings; a project setting otherwise cannot re-enable a global opt-out. Settings changes synchronously clear queued reports, abort requests still in flight, and discard in-progress journey/run aggregates. A request already accepted by the server cannot be recalled. Environment flags are checked before capture and delivery. No opted-out history is replayed on re-enable.

The existing random installation UUID remains in `telemetry.json` with private file permissions. It is not derived from a machine, account, email, IP address, repository, or credentials. Independent analytics UUIDs identify sessions, runs, error occurrences, onboarding attempts, and feature attempts. Optional daemon prompt metadata uses the negotiated `telemetry_input` capability and schema revision 28. Clients remove it for older supervisors/workers; no startup dependency or protocol-version bump is introduced. Root sessions own run telemetry so attached UIs and subagents do not duplicate root run counts.

Only contract-listed properties reach the transport. Provider/model/tool names become fixed categories, including `custom`; operational IDs are random UUIDs. Error reports preserve the separate reviewed `diagnostic_message` and legacy `error_code`, and add a bounded `error_code_group` for provider, HTTP, operating-system, process-exit and signal codes. Group by component and code, with type/subtype fallback when a code is missing; do not group by message text.

Error-message policy revision 1 preserves exact Prime Agent wording only when it matches a reviewed, fixed message in the shared contract. The client requires its approved `error_message_id` and exact text; a claimed source or error type does not authorize arbitrary text. Credential filters cover authentication/cookie headers, token/key/password assignments, URL credentials, private keys and recognized token formats. The collector validates only the bounded transport shape before forwarding to PostHog. A message that changes under credential filtering is rejected. The finite message policy is the primary safeguard against prompt content; credential patterns alone cannot identify a prompt echoed by a provider or tool.

An arbitrary Error, provider response, tool result, extension error, cause or log entry is never forwarded as message text. Recognized system codes can produce a fixed description with paths, addresses and arguments omitted. `error_message_source=reviewed_literal` means the exact original wording was retained; `system_template` means a fixed description was substituted. Other failures retain their code, type, subtype and reviewed `diagnostic_message` without `error_message`. Codes also use reviewed values or bounded HTTP/RPC/process/signal formats, so an arbitrary code cannot carry prompt text. Reports exclude prompts, responses, reasoning, tool arguments/results, request bodies, stack traces and logs.

The existing 4,096-character message limit and length/transformation fields remain in the contract. Accepted messages are shorter fixed strings; their length and flags are reconstructed from that safe text, never from rejected content or caller-supplied metadata. A message reaches the transport only when the collector advertises `original_error_messages=true` and the same `error_message_policy_revision`. Older collectors still receive supported code/timing metadata without message fields. When the collector advertises `posthog_exception_events=true`, Prime Agent constructs an additional PostHog `$exception` event for each explicit error occurrence after sanitization and message-policy negotiation. Platform forwards it without interpreting error fields or generating another event. Older collectors receive the existing analytics format, avoiding duplicate exceptions on collectors that still generate them server-side. Recovery updates and ambiguous older records do not create additional exceptions. The mirror uses the same event time, a deterministic distinct event ID, and a code-based fingerprint; its value is the accepted message or reviewed diagnostic, with the source identified. It does not attach stacks, causes or breadcrumbs.

To reset the local analytics identity, first close all Prime Agent processes using the agent directory, then remove its `telemetry.json`, `telemetry-onboarding.json`, and `telemetry-installations/` state. The next enabled launch creates a new unrelated installation ID. This does not delete previously accepted server data. Opting out does not rotate the existing installation ID.

`PRIME_AGENT_TELEMETRY_ORIGIN=internal` or `test` explicitly marks internal/test activity. Other origin values are not uploaded. Interactive and noninteractive execution remain separate; an execution mode does not prove whether a human or automation initiated the work.

## Event compatibility

The machine-readable [contract](telemetry-contract.json) is mirrored by `src/core/telemetry-contract.ts`; client tests enforce equality, including the reviewed message and code registries. Platform maintains only the generic transport schema, including bounded nested JSON for native PostHog properties. Schema version 2 is an additive envelope negotiated through the optional `/api/v1/agent-analytics/capabilities` endpoint. Error-message support has its own policy revision so older collectors degrade safely.

| Event | New detail |
| --- | --- |
| `agent started` | Existing session start plus explicit schema/build/origin categories |
| `onboarding completed` | Existing configured-credentials observation, with its original meaning preserved |
| `agent command used` | Existing fixed command usage categories, with arguments excluded |
| `agent run started` | Independent run ID, input association, per-session run index and categorized execution context |
| `agent run completed` | Paired terminal outcome, successful model-response count, timing coverage, tool/retry/compaction duration, usage completeness, optional estimated cost |
| `agent error` | Narrow subtype, stable code group, reviewed original wording or fixed system description, separate diagnostic, occurrence/recovery distinction and consecutive failures |
| `agent timing` | Separate worker/UI origins, input queue/preparation, provider dispatch, first model/reasoning/text, retry, compaction, time-to-error and cancellation-to-idle durations |
| `agent tool summary` | Per-run tool category counts, failures, later same-tool successes and known duration |
| `agent input stage` | Worker receipt, queue, preparation, admission and terminal observations, including failures before a run |
| `onboarding stage` | Actual setup/check/exit observations with explicit unchecked and canceled states |
| `agent feature outcome` | Attempt and result for a fixed feature, plus optional fixed-choice feedback |
| `agent startup stage` | Measured configuration, connection, UI rebind, and readiness stages |
| `agent session ended` | Existing totals plus observed shutdown outcome |
| `agent installation stage` | Revision-3 install/update attempt, download/verification/package result, daemon/session/relaunch outcome, and separately observed runtime readiness with safe version comparisons |

The original five event names, required properties, broad error categories, outcome values, and stable installation identity are preserved. Legacy collectors receive only the original property sets; `homebrew` is mapped to their existing `unknown` value. New event types stay queued until support is advertised. Installation stages additionally require a collector advertising schema version 2 and revision 3 or later; revision-2 collectors continue receiving their supported events. A collector rollback causes a safe legacy retry with the same event ID. New fields are never backfilled or inferred for old events. See [journey definitions](telemetry-journeys.md) for installation, onboarding, feature, and startup boundaries.

## Counting and timing

Count **distinct installation IDs**, not `agent started` events, for observed installations. Launch/session events measure frequency. Daily unique totals cannot be summed into a monthly unique count. One ID can appear in multiple version/mode breakdowns. First observed telemetry means first seen in available data, not a proven installation date. Installer requests remain a separate aggregate and are not joined to client identities.

Revision-3 installation outcomes measure eligible executions of the shell installer and built-in CLI or interactive updater. Random `installation_attempt_id` values pair stages; deduplicate by installation ID, attempt ID, and stage before counting attempts. `installation_action` distinguishes install from update, and `installation_source` distinguishes shell installer, CLI and interactive UI. Package installation, installer/update command completion, daemon restart, session restoration, relaunch and working runtime readiness are separate observations. Restoration counts include failed session recreation and incomplete queued work; older restart results without complete restoration evidence remain unavailable. Readiness comes from a fresh interactive or headless process, including a ready agents view, after package installation. An absent completion or ready report is unknown, not an inferred failure. Safe previous/requested/observed versions permit mismatch analysis without collecting download URLs, package-manager output, paths or custom version labels. Installs or updates performed independently through a package manager remain outside this funnel.

Run reliability uses distinct `(installation_id, session_id, run_id)` pairs. `terminal_outcome` distinguishes success, error, cancellation, interrupted shutdown, and unknown. A start without a terminal observation is missing coverage; it is not evidence of a crash or abandonment. `successful_model_call_count` counts completed assistant responses with stop, length or tool-call outcomes, excluding failed and aborted responses. It can remain positive when a later tool or session action fails, separating observed inference access from whole-run success. Missing counts on older clients are unknown coverage, not zero. A successful run means the agent loop completed, not that the user's objective was achieved.

Each observed failure is recorded even if a retry later succeeds, including scoped daemon, filesystem, subprocess, authentication and runtime failures. Recovery observations reuse its `error_id` with a new transport event ID. `error_event_kind=occurrence` identifies the original failure; `recovery_update` describes later observations, including scoped manual retry, credentials/model/provider changes. Consecutive failure counts reset on observed successful recovery. Count distinct error IDs and select the latest recovery observation; counting every `agent error` event would overcount failures. Wrapped exceptions are locally deduplicated for a bounded interval. Billing, quota, permissions, unavailable providers, and rejected credentials are separate. Generic HTTP 401 remains ambiguous; it does not prove a key expired. Existing retry and credential recovery behavior is preserved when the provider explicitly classifies a failure as an authentication problem. Structured 402/403/503 failures no longer trigger incorrect credential-stale handling.

Local durations use a monotonic clock. `run_to_first_text_ms` starts at `agent_start`; legacy visible TTFT starts at the first turn. Neither measures user submission or queue delay. Revision 2 adds `input_to_run_ms` from worker receipt, disjoint `queue_wait_ms` and `local_preparation_ms`, plus explicit timing origins. UI durations stay on the UI clock. `provider_dispatch` ends in the SDK stream wrapper immediately before `streamSimple`, after resolving credentials and merging request headers; it is not a measurement of a network write. First-status timing uses an observed terminal render only when it can be attributed to one idle-origin input; ambiguous queued or overlapping inputs report unavailable coverage. First-reasoning latency can be absent for models that do not expose reasoning. Maximum stream gaps cover observed model events within a call, including the terminal edge, and exclude time spent running tools. Tool times can overlap, so their sum is work duration rather than elapsed run time. Missing tool start or unfinished tools produce null duration. Pending or failed model calls make `usage_complete=false`. Cost is an estimate from known pricing for every observed call and is null when any price/usage is unknown; it is not a billing ledger. Output tokens divided by model latency is an effective request rate including initial wait, not pure generation throughput.

Manual and pre-run compactions also emit session-scoped timing with success, error, cancellation or interrupted-shutdown outcomes. They are not attached to an unrelated later run; run compaction totals include only work owned by that run.

Dashboard percentiles must show sample counts and missing-value coverage. Mature 24-hour/D1/D7 cohorts exclude installations whose observation window has not elapsed. Successful runs are required for activation and repeat-success metrics. Missing association is reported separately from observed failure.

## Delivery and deployment

Capture does not wait for network delivery. A process holds at most 256 sanitized reports in memory, sends at most 20 events and 30 KB per batch, and expires reports after five attempts or 24 hours. Retries keep transport IDs and back off to at most 60 seconds. Background delivery has a seven-second budget; session shutdown waits at most 1.5 seconds. Partial acknowledgements remove only accepted or rejected IDs, including independent acknowledgement and retry of an analytics event and its native exception. Discovery is optional and bounded; it never prevents startup. Collector delivery acknowledges the upstream batch and deduplicates retries. Delivery errors never recursively create analytics errors.

Telemetry is best effort. Opt-outs, offline operation, endpoint failure, rate limits, queue overflow, abrupt process exit, and missing observations reduce coverage. There is no disk event spool: a hard crash, forced kill, or restart can lose queued events. Controlled startup failures flush within the same 1.5-second shutdown budget. The fatal exception monitor preserves normal Node exit behavior; it cannot guarantee a final network report. Background log and exception reporting require a known operation-specific consent context. Resident daemon session commands use their own effective session consent context. Unbound/shared catalog failures remain in caller-side reporting paths; one project's settings cannot authorize reports for another project. Catalog bootstrap failures use the catalog's effective settings and inherited environment without enabling global request reporting. Local delivery counters expose accepted, rejected, expired, overflow, retry, and unavailable counts for diagnostics; collector operational counters measure its own accepted/dropped/retried traffic. These are not a census of lost client events.

1. Deploy the backward-compatible Platform collector first ([Platform PR #5228](https://github.com/PrimeIntellect-ai/platform/pull/5228)). Confirm legacy acceptance, v2 capability discovery, partial acknowledgement, duplicate IDs, and rollback behavior in staging.
2. Inspect proxy/CDN/access logs, tracing, and PostHog ingestion transforms for metadata enrichment. The collector strips sensitive payload/transport metadata and disables person/GeoIP enrichment; infrastructure outside the application needs a deployment-level check.
3. Release the client. Use synthetic, content-free canaries to verify both enabled delivery and complete opt-out. Compare healthy and failed runs, retry recovery, canceled setup, warm attach, and old/new client combinations.
4. Validate v2 property coverage in PostHog before publishing the new dashboard bundle. Its publication script defaults to preview and refuses to publish new charts without observed v2 data. Existing count corrections and new definitions are versioned for review; the implementation PR does not deploy or alter live dashboards.

The reviewed [dashboard bundle](telemetry-dashboards.json) includes seven historical chart corrections and 30 views for errors, activation, retention, features, timing, coverage, execution context, installation/update outcomes and alert samples. The three installation views cover attempt completion versus runtime readiness, stage outcomes/timing, and previous/requested/running versions. They require revision-3 data; existing revision-2 views retain their revision-2 gates. From the repository root, `node scripts/publish-telemetry-dashboards.mjs --check` validates the local bundle without network access. `--preflight` uses `POSTHOG_PERSONAL_API_KEY` to verify the target project, existing chart shapes, query results, and observed events at each view's required revision without changing dashboards. `--apply` performs those checks before writing; charts without required observations remain pending. `--legacy-only` limits preflight or publication to the historical corrections. Run preflight and review its result after deployment before choosing apply. `--include-alerts` creates three disabled native PostHog alerts without subscribers: failed-run fraction above 10%, aged missing terminals above 5%, and a reporting-volume drop above 75%. The first two require 100 observations and 10 installations; the drop check requires the same baseline minimum. These are proposed starting thresholds. Choose recipients, check real baseline behavior and enable alerts separately in PostHog.

PostHog aggregation reference: [supported SQL aggregations](https://posthog.com/docs/sql/aggregations).
