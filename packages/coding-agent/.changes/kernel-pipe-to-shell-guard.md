- Added a pipe-to-shell guard to the kernel bash tool: a `curl`/`wget` download that feeds a shell interpreter is refused before any process starts, because that runs remote code with no review step and no record of the bytes that ran. Both shapes are matched from the command text alone, so nothing is fetched: a pipeline stage whose command word is `curl`/`wget` that feeds a later stage of the same pipeline whose command word is a runner (`sh`, `bash`, `zsh`, `dash`, and the shell's own `eval`/`source`/`.` forms, through an intermediate stage as in `curl ... | cat | sh`, and through a stage whose own command word is a substitution that runs the download, `$(curl ...) | sh`), and a `$(...)`, backtick, or unquoted `<(...)` payload whose command word is `curl`/`wget` used as an argument of a runner (`sh -c "$(curl ...)"`, `bash <(curl ...)`, `source <(curl ...)`), plus the words the runner itself executes, the script a `-c`-style flag hands an interpreter (`sh -c "curl ... | sh"`, `bash -lc "..."`) and every argument of `eval` (`eval "curl ... | sh"`). `<(...)` is the read mirror of process substitution, whose output a runner reads as a file; the write mirror `>(...)` is read too, because the bytes the command writes into it are that process's stdin, so a runner there executes them (`curl ... > >(sh)`). Wrapper commands are read at both ends, so the command word behind one is the command: `env curl ... | sh`, `env -i curl ... | sh`, `nice 5 curl ... | sh`, `stdbuf -oL curl ... | sh`, `curl ... | env -i sh`, `curl ... | sudo -u root env sh`, `curl ... | xargs sh`, `curl ... | busybox sh`; the lookup form `command -v curl` is not a command word and stays allowed. A download stage that feeds an interpreter is refused whatever the download's own flags say, so `curl -o /tmp/x URL | sh` and `command -p curl --version | sh` are deliberate over-refusals. The scan reads words the shell's way, so quoted command words still run the command (`"curl" ... | sh`, `cu"rl" ... | sh`), redirections, assignments, and privilege prefixes hide neither end (`2>/dev/null curl ... | sh`, `FOO=1 curl ... | sh`), line continuations join the words they split, ANSI-C quoting that spells its word plainly builds it while an escape in it (`$'cur\x6c'`) leaves the word unresolvable and the receiver side refuses it, and single-quoted data and comments stay inert (`echo 'curl | sh'`, `echo hi # curl | sh`). A download that feeds a stage the scan cannot resolve (`curl ... | $SHELL_CMD`, `curl ... | "$(echo sh)"`) is refused rather than allowed, and a region an unterminated quote left unresolvable is re-read with its quote characters dropped for the same reason. The shape is read through the shell's own prefixes: a bang negation (`! curl ... | sh`), the reserved words of `if`/`while`/`for` compounds, and a brace group at either end (`curl ... | { sh; }`, `{ curl ...; } | sh`), where the separators inside a group keep the chain instead of ending it. `eval` concatenates its arguments into one script before the scan reads them, so a pipeline spelled across arguments (`eval "curl ..." "|" sh`) is read joined. A here-document body is the script of the stage that owns it, quoted delimiter or not, because the stage executes its text either way: a runner (`sh <<EOF`) runs the body, and a stage whose stdout continues into a runner hands it the body (`cat <<'EOF' | sh`); a body of a stage that is not a runner stays data, except that the shell expands an unquoted body at read time, so a `$(curl ... | sh)` inside one runs whatever the owner (`cat <<EOF`). Wrapper value operands no longer hide the command behind them (`timeout 30s curl ... | sh`, `curl ... | xargs -I {} sh`), a wrapper-only `sudo -s`/`sudo -i` stage is a shell reading the pipe (`curl ... | sudo -s`, also through value flags like `sudo -s -u root`), and an unresolvable producer command word fails closed like the receiver side, so `$(printf curl) URL | sh` is refused and `$(date) | sh` is a deliberate over-refusal. Downloading to a file or into a redirect (`curl -o /tmp/x URL`, `curl URL > /tmp/x`), reading a download downstream (`curl ... | jq .`, `curl ... | grep name`), handing one to a non-runner (`diff <(curl a) <(curl b)`), and the two-statement download-then-run sequence are untouched; the scan costs one pass over the command's text, multiplied by the nesting it holds — substitutions and here-document bodies alike — which a depth cap bounds. A receiver that is a function defined in the same command text (`run(){ sh; }; curl ... | run`) or a function supplied through the environment (`BASH_ENV`, an exported `BASH_FUNC_*`) is out of the modeled set, because that receiver has to be built deliberately instead of met by accident: the guard stops accidental pipe-to-shell, not receiver functions built to run code, and the environment-supplied route belongs to the planned shared shell-invocation analyzer (exported functions, startup files, hash aliases). Other shells (`ksh`, `fish`) and other interpreters (`python3 -`) are deliberately out of scope. Explicit bypasses: `bash(command, allow_pipe_to_shell=True)` or `PI_BASH_ALLOW_PIPE_TO_SHELL=1`, where the env bypass is frozen at kernel start so mid-session `os.environ` writes cannot neuter the guard (they are ignored and warned about loudly).
