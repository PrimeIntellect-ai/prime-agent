- Added a secret-echo guard to the kernel bash tool: a bare environment dump (`env`, `printenv`, `export`, `export -p`, and flags-only forms such as `env -0`) or a `cat`/`echo` of a file under one of the secret directories in the home directory (`~/.ssh`, `~/.gnupg`, `~/.aws`, in either the `~` or the `$HOME` spelling) is refused before any process starts, because that output persists in session logs that models and users read later. The dump test is shell-faithful: leading `FOO=1` assignments are stripped first (`FOO=1 env` is a bare dump in disguise), the operand of `-u`/`--unset`/`-C`/`--chdir` is that flag's own and not a command word (`env -u PATH` still dumps), and a nested dump word dumps too (`env printenv`, `env -S 'env'`, `env -i printenv`), while `env printenv HOME` is the targeted read it looks like and the `-S`/`--split-string` operand is read as the whole command line it is (`env -S 'printenv HOME'` is that same targeted read, while `env -S 'printenv'` and `env -S 'env -0'` still dump), redirections are ignored because they never narrow what is printed (`env 2>/dev/null`, `env 2>&1`, `env > /tmp/x`, and the glued spellings `env>&2` and `env>/dev/null`, where a redirection is split off the command word it is glued to, while a word that starts with the `&>` operator (`env &>/dev/null`, `&>log cat ~/.ssh/id_rsa`) is left whole so the real command word keeps its place; a `&` glued to `>` is a redirect spelling, not a background operator, so `env 2>&1 | grep PATH` stays a piped read and a filtered dump redirected to a file stays the allowed read), and quoted command words and concatenations are canonicalized (`"env"`, `ca"t"`, and the ANSI-C and locale spellings `$'env'` and `$"env"` still run the command); `$HOME` glued to a secret path matches even across a closing double quote (`cat "$HOME"/.ssh/id_rsa`). Both spellings are read from the word the shell builds, so a quote inside the path does not hide it (`cat ~/".ssh"/id_rsa`, `cat ~/'/'.ssh/id_rsa`, `cat $HOME/".ssh"/id_rsa`, and `cat "$HOME""/.ssh/id_rsa"` all read the key), while a `~` the shell never expands stays the literal text it is: it has to be the first character of the word and the character right after it has to be the `/` of a path, read from the command text rather than from the mask, so `cat "~/.ssh/id_rsa"`, `cat '~'/.ssh/id_rsa`, and `cat ~'/'.ssh/id_rsa` are text while `cat ~/'/'.ssh/id_rsa` (the quoted slash is still the slash after the tilde) reads the key, and a `$HOME` has to be live in the mask that leaves double quotes live, so `cat '$HOME/.ssh/id_rsa'` is text. An executor form is read the same way: the command word `env` runs the command line its remaining words name, so `env cat ~/.ssh/id_rsa`, `env echo ~/.ssh/id_rsa`, and `env FOO=1 cat ~/.ssh/id_rsa` refuse, and the `-S`/`--split-string` operand of that form is read for the `${VARNAME}` spelling `env` expands inside it (`env -S 'cat ${HOME}/.ssh/id_rsa'` refuses) while a `~` in that operand stays literal text and reads nothing (`env -S 'cat ~/.ssh/id_rsa'` reports no such file). A command substitution runs another command, so the interior of every `$(...)` and backtick span is scanned the same way, including inside double quotes (`echo "$(env)"` is refused) and including a substitution inside arithmetic (`echo $(( $(env) ))` is refused, while `echo $((env))` is the number the arithmetic reads and runs nothing, because `$((` opens an arithmetic expansion rather than a command and the parentheses of an expansion are syntax rather than segment separators: bash reads `echo $((env))` that way only while the two `)` closing it are adjacent, and reads `echo $((env) )` as `$( ( env ) )`, the subshell that runs env and prints the whole environment, so a `$((` whose closers are not adjacent is scanned as the command substitution it is and still refuses while a targeted read inside one (`echo "$(printenv HOME)"`) still runs, at any nesting depth (`"$(echo "$(env)")"` is refused) and iteratively, because interiors come from a worklist so nesting depth cannot exhaust the Python stack, so a command built out of thousands of unterminated openers is scanned in one bounded pass, and a line carrying thousands of here-document openers costs one short word read each because only the delimiter word is lexed (the same 8000-opener line answers in about 0.08s). A benign nest is still super-linear in the length of the command, and a leak at any depth refuses on the spot; the body of a here-document is never shell input, quoted delimiter or not, so `cat <<'EOF'` and `cat <<EOF` with `env` on a body line only print that text, while a dump built by a substitution in an unquoted body (`cat <<EOF` with `$(env)`) is still refused and the line that closes a body is skipped by that walk as well, because it is the syntax that ends the body and expands nothing (`cat <<'$(env)'` with `$(env)` on the closing line prints its body word instead of being refused, while a body closed by a dump word (`cat <<'env'`) stays refused), and a `<<` inside an arithmetic command (`(( x = 1 << 2 ))`, the deprecated `$[ 1 << 2 ]`, `$((1<<y))`) is a shift that opens no body, so the lines after it still run (`let a=1<<2` is a real opener, which is why only the arithmetic spelling suppresses the body). Single-quoted spans, comments, and the character a backslash escapes are masked so echoed strings, quoted data, and literal text (`echo \$HOME/.ssh/id_rsa`) stay inert (a comment counts for this too: `echo hi # $(env)` prints `hi` and runs nothing), while quoted operands stay single words (`env 'foo&bar'` stays an executor form). A bare dump piped into `grep` is still allowed as the targeted read the refusal suggests, narrowed to a fixed-string single-key filter: an inverted (`-v`), file-supplied (`-f`), NUL-record (`-z`/`--null-data`, which makes the whole dump one record any pattern matches), context-widening (`-A`/`-B`/`-C`, the bare-number `-2` spelling of `--context`, and a digit inside a cluster such as `-10i`, `-i2`, or `-F2`), abbreviated long-flag (`--cont=2`, `--after-c=2`), empty, substitution-built (a backtick pattern), or regex pattern is refused, while `-F`/`--fixed-strings` and other bounded flags pass (a digit run directly after an `m` is that flag's own bound, so `-m1`, the spaced `-m 1`/`--max-count 1`, and `-F -m1` pass while `-1m` is refused, unless the count is zero, which prints the whole dump here and is refused (`-m0`, `-m00`, `--max-count=0`, and the glued abbreviation `--max-c=0`, since grep reads any unambiguous prefix of a long option name), while a `--` word ends the options the way grep reads them, so the `-v` of `env | grep -- -v` is one fixed-string pattern rather than inversion and `env | grep -- -v KEY` is two operands and stays refused); the dump has to reach the pipe for the exemption (`env 2>&1 | grep PATH` and `env 2>/dev/null | grep PATH` stay allowed, while `env >&2 | grep PATH` moves fd 1 to stderr and `env >log | grep PATH`, `env &>log | grep PATH`, `env >>log | grep PATH`, `env >/dev/null | grep PATH`, and a `<>` open on stdout (`env 1<>/dev/stderr`, `env <>log`) send it elsewhere, so all of them are refused because the dump never reaches grep, while a `<>` on another descriptor (`env 0<>log`) leaves fd 1 alone), the shell reads a newline after the pipe as the pipe continuing, so the follower is still the grep the pipe feeds (`env |` with `grep KEY` on the line below is the same filtered read) while a dump on the line below (`env |` then `env`) stays refused, and the descriptor of that redirection is read after quote removal, so only a plain unquoted digit run is trusted: a quoted, escaped, expanded, or substitution-built descriptor (`>&"2"`, `>&\2`, `>&${X}`, ``>&`printf 2` ``) is refused as moving fd 1, as are a target that is not a descriptor at all (`>&2x` writes a file, `>&-` closes the descriptor) and the left-to-right swap `2>&1 1>&2`, which are fail-closed refusals of commands that do not leak; `.env`-class files, directory listings, `printenv VAR`, `env FOO=1 cmd`, and `export FOO=1` are never matched. The guard reads the script the handle runs, prefix included, and that script is computed once per call, so a change to `PRIME_AGENT_BASH_COMMAND_PREFIX` between validation and execution cannot make the validated text differ from the executed text (a prefix that dumps the environment is refused like any other dump); a `BashHandle` built directly, without the validated script `bash()` passes, is guarded in its constructor instead, so the class is not a way around the guard while the `bash()` path pays no second scan. Explicit bypasses: `bash(command, allow_secret_echo=True)` or `PI_BASH_ALLOW_SECRET_ECHO=1`, where the env bypass is frozen at kernel start so mid-session `os.environ` writes cannot neuter the guard (they are ignored and warned about loudly).

- Known limitations, so this is not read as a sandbox. This guard stops the ordinary foot-gun; it is not a sandbox, it has no filesystem access, and it reads the shape of the command rather than the file: only `cat`/`echo` are modeled as readers, so a reader it does not name (`head -c 20 ~/.ssh/id_rsa`, `sed`, `grep` on a secret file, and the executor form `env head ~/.ssh/id_rsa`) is not matched; the secret-path rule names the directories (`.ssh`, `.gnupg`, `.aws`) rather than the files in them, so a `cat` of a file there that holds no key is refused too (`~/.ssh/config`, `~/.ssh/known_hosts`, `~/.ssh/id_rsa.pub`, `~/.aws/config`), which is also what keeps the rule holding however the file inside is spelled, because the match is on the directory and not on the name (`cat ~/.aws//credentials`, `cat ~/.aws/./credentials`, `cat ~/.aws/../.aws/credentials`, and `cat ~/.aws/cred*` all refuse, and `cat ~/.awsrc` and `cat ~/.aws.old/x` do not match), and a path is refused whether or not it exists; a backslash-newline line continuation is not modeled, and the three passes read the pair differently: `_shell_words` keeps it in the word it builds, `_mask_literals` blanks it as two characters, and `_paren_matches` takes its word state from it, so `e\` with a newline then `nv` runs the whole environment, `ca\` with a newline then `t ~/.ssh/id_rsa` reads the key, and `echo x\` with a newline then `#; env` runs a command the mask hides; the continuation-aware word model belongs with the one-pass linear rewrite tracked separately, and is not modeled here; a command word the scan cannot resolve is out of the modeled set (a path such as `/usr/bin/env`, a wrapper such as `command` or `eval extra word`, an expansion such as `${x:-env}`, or a keyword or group in front of the command word, such as `{ env; }`, `! env`, `if true; then env; fi`, or the body of a `for`/`while` loop); and an operand that expands to nothing (`env $EMPTY`, `env $(echo)`) leaves the bare dump this guard refuses when the operand is absent, and is not modeled, because no text-only scan can know whether the expansion is empty; and a here-document body that is closed by a delimiter line which is itself a dump word (`cat <<'env'` with `env` on the closing line) is refused rather than read as syntax, because the word checks still read that line.
- Known cost limitation, tracked for a separate change: a benign nest that closes over the next level (2400 deep, about 24KB) costs about 14s, while a flat command of the same length costs under 0.05s and the base before this guard answered the nest in 0.002s. Every nesting level is read in its own quoting context, which is what makes the scan super-linear in the length of a nested command; a one-pass linear rewrite is planned separately, and no depth or work cap is added to that walk, so the guard answers a command of any depth: the one bounded re-test is the nested command line an `env -S` operand carries, which answers as a dump past its bound instead of raising, fail closed.
